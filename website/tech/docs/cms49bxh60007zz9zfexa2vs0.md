## 开篇痛点：环境配置总踩坑？一份清单直接复用

跑通 Claude Code 前，90% 的卡点都不是用法问题，而是环境。手册中专门留出一节“5 分钟环境检查”，这里提炼成三件事：

1. **Node 版本**：18+ LTS，别用奇数版本。
2. **API 密钥**：环境变量 `ANTHROPIC_API_KEY` 设置后，必须用 `claude --version` 验证连通性。
3. **代理**：如有代理，需同时设置 `HTTP_PROXY` 和 `HTTPS_PROXY`，且 `no_proxy` 中不能包含 `api.anthropic.com`。

下面展开每条对应的报错和修正动作，跟着走一遍，10 分钟足够从零跑通。

### Node 版本：安装成功却报 “SyntaxError”

常见场景：用 nvm 安装了 Node 20，运行 `claude` 却抛出 `SyntaxError: Unexpected token '??='`。原因往往是当前终端使用的 Node 版本仍为系统自带的 v14 或 v16，`??=` 运算符在 v15.14.0 才引入。

**修正动作**：执行 `node -v` 确认活动版本；若不是 18+，重新 `nvm use 20` 或 `nvm alias default 20`。若全局安装后依然报错，检查 `which claude` 路径是否在 nvm 管理目录下，必要的话删掉旧版本：`npm uninstall -g @anthropic-ai/claude-code && npm install -g @anthropic-ai/claude-code`。

### API 密钥：配置了变量却 “401 Unauthorized”

几乎每次环境问题都绕不开这一绊子。错误信息：`Error: Request failed with status code 401` 或 `Invalid API key`。检查四步：

1. **变量是否真的存在**：`echo $ANTHROPIC_API_KEY` 看输出，很多人在 `~/.bashrc` 写了 export 但忘记 `source`。
2. **key 是否有效**：在 [Console](https://console.anthropic.com/keys) 确认状态为 Active，权限至少勾选 “Claude Code”。
3. **终端环境**：如果通过 IDE 内置终端启动，可能继承了旧的环境变量。手动在终端执行 `export ANTHROPIC_API_KEY=sk-ant-xxxx` 临时测试。
4. **验证连通**：运行 `claude --version`，若返回版本号，说明鉴权通过；否则会有明确错误。

修正后若仍 401，打开代理排查。

### 代理设置：卡在 “connect ETIMEDOUT”

公司网络或科学上网环境下，最常见报错是 `connect ETIMEDOUT xxx.xxx.xxx.xxx:443`。Claude Code 默认直连 `api.anthropic.com`，不读取系统代理。需显式设置：

```javascript
export HTTP_PROXY=http://127.0.0.1:7890
export HTTPS_PROXY=http://127.0.0.1:7890
export NO_PROXY=localhost,127.0.0.1,.local
```

注意 `NO_PROXY` 不要包含 `api.anthropic.com`，否则代理绕过导致超时。如果代理需要认证，格式为 `http://user:pass@proxy:port`。设置后立即 `claude --version` 验证，正常返回版本号即表示已通过代理连接。

以上三条按清单顺序过一遍，手册里 95% 的环境问题都覆盖了。跑通之后，下一节我们再拆解高频提示词模板。

## 核心交互：10个高频提示词模板，覆盖单元测试到重构

手册整理了10个真实场景的提示词，每条都经过反复验证，附有输入示例和 Claude 返回的关键片段，可直接复制到编辑器查看效果。

1. **单元测试生成**
场景：给一个函数，需要自动生成覆盖边界情况的测试用例。
提示词：

```bash
为下面的 TypeScript 函数生成 Vitest 测试，覆盖正常值、空数组、负数输入和类型错误的情况，使用 describe/it 结构。
```

Claude 会输出完整的测试文件，包含 mock 和断言，例如：

```javascript
describe('calculateDiscount', () => {
  it('returns correct price with valid discount', () => { ... });
  it('throws on negative price', () => { ... });
  it('handles empty items array', () => { ... });
})
```
2. **重构函数**
场景：一段长函数需要拆分成更小的可复用单元，同时保持逻辑不变。
提示词：

```
重构以下 Python 函数，拆成不超过15行的子函数，保持原有单元测试通过，不要改变任何公开接口。
```

Claude 会返回重构后的代码，并说明每个子函数的职责，例如将数据处理、验证和格式化拆分为独立函数。
3. **调试报错**
场景：粘贴一段报错堆栈，需要快速定位原因和修复方案。
提示词：

```css
这个 Rust 编译错误（错误信息：`cannot borrow `x` as mutable more than once at a time`）出现在第47行，解释具体原因并给出修改建议。
```

Claude 会指出哪里发生了多重可变借用，并提供两种修复方案（如调整作用域或使用 RefCell）。
4. **解释代码逻辑**
场景：接手陌生代码库，需要快速理解一段晦涩的 SQL 或正则。
提示词：

```sql
用中文解释这条 PostgreSQL 查询的每一步作用，并指出可能的性能瓶颈：SELECT ... FROM orders WHERE ... GROUP BY ... HAVING ...
```

Claude 会逐句翻译成业务含义，并标注索引缺失点。
5. **性能优化**
场景：一个接口响应慢，需要优化算法或数据库查询。
提示词：

```
这个 Node.js 端点在高并发下延迟超过500ms，分析代码并给出至少两种优化方案，附带时间复杂度对比。
```

Claude 可能指出 N+1 查询，并给出批量查询或缓存方案。
6. **添加文档注释**
场景：为已有代码补全 JSDoc 或 docstring。
提示词：

```
为以下 React 组件生成 JSDoc 注释，描述 props、状态和副作用，保持英语注释。
```

Claude 会输出带完整注释的组件代码，包括 @param 和 @returns。
7. **语言/框架迁移**
场景：将一段代码从 Python 转为 Go，保持相同功能。
提示词：

```
将这段 Python 数据处理脚本转换为 Go 语言，使用标准库，保持相同的输入输出和错误处理行为。
```

Claude 会重写代码，可能自动忽略 Python 的动态特性，改用结构体和方法。
8. **生成 API 端点**
场景：给定数据模型，快速生成 CRUD 路由和验证逻辑。
提示词：

```
为这个 Prisma 模型生成 RESTful 端点（Express），包含创建、列表（分页）、单个查询和删除，附带输入验证和错误码。
```

Claude 会给出完整的路由文件，包含 try/catch 和 404 处理。
9. **代码审查反馈**
场景：让 AI 模拟评审，指出潜在问题和改进建议。
提示词：

```
审查以下 Go 代码，指出不符合最佳实践的地方、线程安全问题，并给出修改后的代码片段。
```

Claude 会列出具体行号的问题，如未关闭资源、潜在的竞态条件。
10. **编写一次性脚本**
场景：需要快速处理日志文件、迁移数据等临时任务。
提示词：

```
写一个 Bash 脚本，读取 access.log，统计每个 HTTP 状态码的出现次数并按降序排列，输出到 result.txt。
```

Claude 会给出可直接运行的脚本，并提醒执行权限。

每个模板的关键是**给足上下文**（语言、框架、边界条件）和**明确输出格式**，避免模糊描述。实际使用时替换其中的具体代码/路径即可验证。

## 多文件编辑：两个案例讲清「代码地图」用法

多文件修改最怕遗漏——重命名一个函数，可能散布在十几个文件中；引入一个新库，要改依赖声明、多处导入和调用点。直接让 Claude 一次性跨文件修改，不仅容易漏改，还可能引入不一致的代码风格。手册推荐的做法是：**先地图，后行军**——让 Claude 先画出受影响文件的全景图，逐文件确认后再精准修改。

工作流拆为两步：

1. **画地图**：给出明确搜索指令，要求 Claude 列出所有受影响文件、行号及当前代码片段，以结构化清单输出。
2. **逐文件改**：根据清单，一次只改一个文件，每步验证后再继续。这样任何一步出问题都能立刻定位，不会污染其他文件。

### 案例一：跨文件重命名 API

假设你要把全局函数 `getUserName` 重命名为 `getFullName`。直接说“帮我全局替换”风险极大。正确做法：

**第 1 步：生成地图**

> 提示词：搜索项目中所有使用 `getUserName` 的地方（包括调用、赋值、注释），列出文件相对路径、行号和对应完整行内容，以 Markdown 表格输出。

Claude 会返回类似这样的清单：

```javascript
| 文件路径                  | 行号 | 代码片段                           |
|---------------------------|------|------------------------------------|
| src/utils/user.js         | 5    | export function getUserName(id) {} |
| src/components/Profile.js | 12   | const name = getUserName(userId);  |
| tests/user.test.js        | 8    | expect(getUserName(1)).toBe('...');|
```

人工扫一眼确认没有误伤（例如注释里提到的 `getUserName` 是否需要改？）。

**第 2 步：逐文件修改**

> 提示词：请修改 `src/utils/user.js`，将第 5 行的函数名 `getUserName` 改为 `getFullName`，函数体不变。

改完检查无误后，用同样方式处理下一个文件。这种流水线式修改让每个变更都可追踪，回滚也方便。

### 案例二：引入新库（lodash/debounce）

假设你要在多个组件中用 `lodash/debounce` 替换手写的 `setTimeout` 防抖。如果让 Claude 自己判断该改哪里，它可能漏掉某些组件或误改不相关的计时器。

**第 1 步：生成地图**

> 提示词：找出项目中所有使用 `setTimeout` 实现函数防抖的文件（模式为：在函数内 `clearTimeout` 后重新 `setTimeout`），列出文件路径、行号及上下文代码片段。

Claude 会定位到若干组件文件，例如 `SearchBar.js`、`AutoSave.js`。确认这些确实是需要改造的防抖逻辑后，再进入下一步。

**第 2 步：逐文件添加导入并替换逻辑**

> 提示词：在 `src/components/SearchBar.js` 顶部添加 

```javascript
import debounce from 'lodash/debounce';
```

，然后将第 20-25 行的 `setTimeout` 防抖逻辑改为 `this.handleInput = debounce(this.handleInput, 300);`。保持其它代码不变。

改完一个文件后运行测试或手动检查，确保行为一致，再继续下一个文件。

**核心价值**：先画地图，把 Claude 从“需要理解整个代码库”的重任中解放出来，只让它做擅长的事：按明确指令搜索和进行局部修改。这最大程度避免了跨文件编辑的遗漏与幻觉，让复杂重构变得可控、可验证。

## 避坑指南：手册精选的五类误用与纠正

手册来自实战踩坑，下面五类误用最常见，每个都配了错误交互和修正对比。

1. **盲信生成结果，不加验证**：Claude Code 能直接输出可运行代码，但边界情况可能出错。错误交互：「帮我写一个排序函数，要求O(nlogn)」直接复制结果，未测试空数组或重复元素。修正交互：追加一句「请补充边界测试用例，包括空数组、单元素、重复元素，并说明时间复杂度最坏情况」；跑一遍生成的测试，发现快速排序在重复元素下退化为O(n²)，再让Claude修正为三数取中优化。
2. **一次性提过大需求，上下文崩塌**：单次要求实现整个用户管理系统，包括注册、登录、权限、密码加密。Claude Code 可能生成混合代码，但模块间接口不一致，登录部分用了明文比对。错误交互：「请实现一个完整的用户管理系统，包括注册、登录、权限控制，用JWT」。修正：拆成三步：1）生成注册模块，要求返回加密后的用户对象；2）基于该对象生成登录模块，要求比对 bcrypt 哈希；3）生成JWT签发中间件，要求引用前两步的接口签名。每一步用 `@file` 引用前一步输出，确保接口对齐。
3. **忽略上下文窗口限制，丢失关键信息**：长对话后，Claude 可能忘记最早的要求。错误交互：先让它生成数据库 Schema，聊了10轮后要求生成 API 接口，它忘了主键类型是 UUID，用了自增 ID。修正：在中途使用「总结上下文」指令，如「请总结当前项目的数据模型，以表格形式列出所有字段和类型」；或开启新对话，手动粘贴关键 Schema 和规范。
4. **把 Claude Code 当搜索引擎用**：直接问「怎么在 React 中实现虚拟列表？」得到通用方案，但未结合项目。错误交互：「请写一个 React 虚拟列表组件」，生成通用代码，未处理项目的拖拽排序需求。修正：提供具体上下文：「以下是我的现有列表组件，它已有拖拽功能。请基于此实现虚拟滚动，保留拖拽排序逻辑，使用 `react-window` 库，并处理动态行高」。附上现有组件代码片段，Claude 才能产出可集成方案。
5. **不指定输出格式，得到一堆解释**：让 Claude 写正则表达式，它先解释语法再给示例。错误交互：「写一个匹配邮箱的正则」，得到 Markdown 段落+代码块，需手动提取。修正：明确指令：「只输出正则表达式，不要解释，用单行字符串形式，边界使用 `/pattern/flags`，并给出2个典型测试字符串和断言」。结果可直接复制，节省时间。

手册中每个误用都附了修正后的提示词模板，可直接套用到自己的对话里。

## 手册的扩展：如何提交你的实战案例

手册的价值在于持续生长。你碰到的真实问题、总结出的有效模板，就是最好的养分。向仓库提交案例不需要复杂流程，但**一致性**会让这份手册长期可用。下面是一套最小贡献规范。

### 什么值得提交

- **可复现的坑**：包含 Claude Code 版本、操作系统、具体报错信息、你尝试过但失败的方法，以及最终解决步骤。
- **模块化提示词**：在 {@prompts} 目录提交 .md 文件，注明适用上下文（如“Java/SpringBoot/多模块项目”）、前置条件、预期效果，最好附带一段前后对比代码。
- **边界用例**：官方手册未覆盖，但你验证有效的用法，例如“用 Claude Code 调试 Docker 容器内远程应用”这类非主流场景。

不要提交纯观点、无验证步骤的“我认为”。

### 使用 PR 模板提交

Fork 仓库后，新建分支命名 `feat/案例简述`，提交 Pull Request 时使用以下模板：

```python
## 案例类型
- [ ] 踩坑记录
- [ ] 提示词模板
- [ ] 边界用法
- [ ] 其他（请说明）

## 环境信息
- Claude Code 版本：
- 操作系统：
- 相关工具链（如语言、框架版本）：

## 问题描述
（简要说明你在什么场景下想做什么，遇到了什么阻碍）

## 解决过程
1. 尝试了什么？为什么没成功？
2. 最终如何解决？附上关键指令或代码片段。

## 验证方法
（审核者如何复现你的场景并验证解决方案）

## 相关知识
（可选的参考资料，如相关 issue、文档链接）
```

模板确保每个案例都包含**上下文、步骤、验证方法**，避免接手的人还要从头摸索。

### 把你的坑变成集体资产

每次提交不仅是贡献，更是梳理。当你写下“环境变量缺少 `CLAUDE_AGENT_MODE=4` 导致工具链不可见”并附上验证步骤，下一个遇见同样报错的人只需 5 分钟搜索就能解决——这就是集体智慧的真实形态。反复出现的案例会被合并进核心章节，署上你的 GitHub ID。
